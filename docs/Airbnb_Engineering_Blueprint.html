Interactive High-Level & System Architecture

The pipeline follows a strict Medallion topology. Raw immutable files land in Bronze, DuckDB transforms them into typed columnar Parquet in Silver, and only the small, query-shaped Gold star schema is pushed to managed Postgres for serving. Heavy lifting never leaves the single EC2 box.

Layer Responsibilities

Bronze (S3)

Byte-for-byte copies of source .csv.gz with capture metadata. Never mutated — full lineage & replayability.

Transform (DuckDB)

In-process OLAP engine on EC2. Reads Bronze, cleans, types, joins — spilling to disk for millions of rows. Zero marginal compute cost.

Silver (S3)

Validated, typed, deduplicated Parquet, Hive-partitioned by city/year. Columnar + compressed = 5–10× smaller.

Gold (Supabase)

Conformed Star Schema in managed Postgres. Small enough for the 500 MB free tier; BI-ready.

Naming Conventions

  • Partition keys as key=value so DuckDB & Athena auto-discover them.
  • Bronze keeps source filename verbatim (listings.csv.gz) for traceability.
  • Silver renames to intent (listings_clean.parquet).
  • Lowercase, hyphen-free city slugs; ISO dates; one logical entity per file.

Manifest Record (per capture)

{
  "source_url": ".../london/.../listings.csv.gz",

  "rows_est": 87421,
  "status": "NEW"   // NEW | DUPLICATE | RETRIED
}

Automated Ingestion Process

  1. Discover. Python reads cities.yaml and resolves each city's current Inside Airbnb data URLs (the get-the-data listing endpoints).
  2. Stream download. requests.get(url, stream=True) with iter_content(chunk_size=1MB) — the file never fully loads into RAM, so a t3.medium (4 GB) handles arbitrarily large archives.
  3. Hash & dedupe. A streaming sha256 is computed during download. If the hash already exists in the manifest index, the file is tagged DUPLICATE and skipped — no re-upload, no reprocessing.
  4. Retry with backoff. Transient failures (timeouts, 5xx, connection resets) retry up to N times with exponential backoff + jitter; permanent failures (404) are logged and surfaced, not retried forever.
  5. Land in Bronze. Verified bytes are put_object'd to the partitioned S3 key, and the manifest row is written atomically.
  6. Idempotent & incremental. Re-running the pipeline only fetches what changed (new hash) — enabling cheap daily snapshots without full reprocessing.

Schemas & Dimensional Architecture

A classic Kimball star: one daily-grain fact surrounded by conformed dimensions. The grain of fact_listings_daily_snapshot is one row per listing per calendar date, sourced from the calendar file and enriched with listing/host/neighbourhood context.

Star Schema (ERD)

Surrogate integer keys (*_key) decouple the warehouse from volatile source IDs, keep the fact table narrow (faster joins, smaller footprint on Supabase's free tier), and leave room for Slowly Changing Dimensions on dim_hosts (e.g., superhost status changing over time).

Validation rules enforced before Gold

  • price >= 0 — negative or null prices flagged, not loaded.
  • -90 ≤ latitude ≤ 90 and -180 ≤ longitude ≤ 180.
  • minimum_nights BETWEEN 1 AND 1125 (drop scrape artifacts).
  • Referential integrity: every fact FK must resolve to a dimension key (anti-join check).

Cost-Control Mechanisms

  • EC2 auto-stop: a systemd watchdog / CloudWatch alarm stops the instance after the pipeline finishes — you pay only for active minutes, not idle hours.
  • S3 lifecycle rules: Bronze objects transition to S3 Glacier IR after 30 days; incomplete multipart uploads auto-abort after 1 day.
  • Compressed everything: .csv.gz in Bronze, Snappy Parquet in Silver — storage & request volume kept tiny.
  • Zero managed-analytics services: no Glue/EMR/Athena/Redshift. DuckDB on the box you already pay for = $0 marginal compute.
  • Free serving tier: Supabase free Postgres (500 MB, 2 vCPU shared) absorbs the entire Gold layer and BI query load.
  • Billing guardrail: an AWS Budget alert at $10 emails before anything approaches the credit limit.
Bottom line. A realistic week costs under $1 and even a careless 24/7-instance week stays near $4 — leaving the overwhelming majority of the $100 credit intact, exactly as the brief demands.

A copilot playbook: paste-ready prompts engineered to generate the three load-bearing scripts of this pipeline. Each prompt pins the stack, constraints, and quality bar so the AI produces production-grade, not toy, code.

🛰️Prompt 1 — Fault-Tolerant Inside Airbnb Ingestioningest.py
You are a senior Python data engineer. Write a single, production-grade module
`ingest.py` that downloads Inside Airbnb files into an S3 Bronze layer.

CONTEXT
- Runs on a memory-constrained EC2 t3.medium (4 GB RAM). Files may be 100s of MB.
- Config-driven: read `config/cities.yaml` listing {city, listings_url,
  calendar_url, reviews_url}. Adding a city must require NO code changes.

REQUIREMENTS
1. Stream downloads with requests(stream=True, timeout=(10,60)) and
   iter_content(chunk_size=1MB) — never load a whole file into memory.
2. Compute a streaming sha256 WHILE downloading. Maintain a manifest index in
   S3 (raw_bronze/.../_manifest.json). If the hash already exists, mark the
   file DUPLICATE and skip the upload entirely (idempotent re-runs).
3. Retry on (Timeout, ConnectionError, HTTP 5xx) up to 4 times with exponential
   backoff + jitter. Do NOT retry on 404 — log and continue.
4. Write to S3 key: raw_bronze/city={city}/year={yyyy}/month={mm}/{filename}.
   Use boto3 with multipart upload for large files.
5. Emit a manifest row per file: source_url, captured_at (UTC ISO),
   bytes, sha256, rows_est, status (NEW|DUPLICATE|RETRIED).
6. Structured logging (logging module, JSON formatter), no print().
   Type hints everywhere, docstrings, and a `def run(config_path)` entrypoint.

CONSTRAINTS: stdlib + requests + boto3 + pyyaml only. Handle partial-download
cleanup. Make every network/S3 call defensively wrapped. Return a summary dict
{downloaded, skipped, failed}. Include a __main__ guard.
🦆Prompt 2 — DuckDB Silver→Gold Star Schema Pipelinebuild_gold.py
You are an analytics engineer expert in DuckDB and Kimball dimensional modeling.
Write `build_gold.py` that reads cleaned Silver Parquet from S3 and builds a
star schema, then loads it into Supabase (managed Postgres free tier).

INPUTS (S3 Silver, Hive-partitioned by city):
  listings_clean.parquet, calendar_clean.parquet, reviews_clean.parquet

TARGET STAR SCHEMA (grain = one listing per date):
  fact_listings_daily_snapshot(fact_id PK, listing_key FK, host_key FK,
    neighbourhood_key FK, date_key FK, price, is_available, minimum_nights,
    est_revenue, reviews_to_date)
  dim_listings(listing_key PK surrogate, listing_id, room_type, property_type,
    accommodates, bedrooms, latitude, longitude)
  dim_hosts(host_key PK, host_id, host_name, is_superhost, host_since,
    host_listings_count)
  dim_neighbourhoods(neighbourhood_key PK, neighbourhood, neighbourhood_group,
    centroid_lat, centroid_lon)
  dim_calendar_dates(date_key PK, full_date, year, month, day_of_week,
    is_weekend, season)

REQUIREMENTS
1. Use DuckDB in-process. Install/load httpfs + parquet; read Parquet directly
   from s3:// using credentials from the EC2 IAM role.
2. Build dimensions first with ROW_NUMBER()-generated surrogate keys; dedupe on
   natural keys. Build the date dimension by generate_series over the calendar
   date range.
3. Build the fact by joining calendar to listings, then resolving every
   surrogate FK via the dims. est_revenue = price * (1 - available_fraction)
   style estimate; document the assumption in a comment.
4. Enforce validation pre-load: price>=0, valid lat/long, FK referential
   integrity (assert zero orphan rows).
5. Load into Supabase using the postgres extension (ATTACH ... AS pg) or psycopg2
   batched COPY. Make it idempotent: TRUNCATE+reload or upsert on natural keys.
6. Wrap each phase in try/except with logging; print row counts per table.

Use parameterized config, type hints, and keep all SQL in well-named DuckDB
relations. Output the full runnable module.

You are an ML engineer. Write `features.py` that turns the Gold star schema into

DATA SOURCE: read from Supabase (or Silver Parquet) the joined listing-level view.
TARGET: log1p(price)  (justify the log transform in a comment — right-skew).

FEATURE ENGINEERING

Open Innovation & Scalability Log

Innovation Idea 1 — Spatial Pricing-Gradient Explorer

A Streamlit + deck.gl app that renders a continuous pricing-gradient heatmap over the city: each hexbin colored by median nightly price, with a slider for room type and a toggle for "premium vs. centre distance." It answers the assignment's geographic-gradient EDA question (§4.2) interactively — a revenue strategist can click a neighbourhood and instantly see its price percentile, listing density, and superhost share.

Data reads dim_neighbourhoods + aggregated fact directly from Supabase. Cost $0 — runs locally or on the same EC2. Impact turns a static finding into a self-serve decision tool.

Innovation Idea 2 — Automated Weekly Market-Intelligence Report

A scheduled job that queries Gold, computes week-over-week deltas (median price, new listings, availability, superhost movement), feeds the numbers to an LLM with a tight templating prompt, and emits a Markdown → PDF stakeholder brief — narrative + charts, auto-generated. Directly realizes the assignment's "Automated Reporting" inspiration and the §7.2 LLM-insight-generation track.

Trigger cron after each ingest. Guardrail LLM only narrates pre-computed numbers (no hallucinated stats). Impact zero-touch recurring deliverable.

Architecture Decision Log

DecisionChosenRejected alternativeRationale & trade-off accepted
Processing engine DuckDB (in-process) AWS Redshift / EMR Spark DuckDB handles millions of rows on one box with $0 marginal compute and zero ops. Trade-off: single-node ceiling — fine at city scale, would need partitioned parallelism at 50+ cities.
Gold warehouse Supabase (Postgres free) Snowflake Free tier, instant Power BI connectivity, real SQL. Trade-off: 500 MB / shared-CPU limits — sufficient for a conformed star, not for raw event volume; we deliberately keep only Gold there.
Silver format Parquet (Snappy) CSV / raw JSON Columnar + compressed = 5–10× smaller, predicate pushdown, typed. Trade-off: not human-readable — mitigated by keeping readable CSV in Bronze.
Compute host Single EC2 + auto-stop Always-on / Lambda / Fargate Pay-per-active-minute; full control, easy DuckDB. Trade-off: cold-start orchestration vs. serverless — acceptable for batch.
Orchestration Python + cron/systemd Airflow / Prefect No standing scheduler infra to pay for or babysit. Trade-off: fewer built-in retries/UI — covered by in-code retry + structured logs; would graduate to Prefect at scale.
